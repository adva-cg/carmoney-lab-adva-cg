# План: добавить комментарий в `backend/public/index.php`

## Файлы

- `backend/public/index.php` — добавить комментарий (содержание, формат и позиция — см. «Открытые вопросы»).
- `docs/plan/plan_<ID>.md` — этот файл (после согласования содержания комментария).

Ничего больше не трогаем. Если нужно сослаться на спеку или раздел AGENTS.md — это станет понятно из ответа заказчика и отразится в разделе «Шаги».

## Шаги

1. Согласовать с заказчиком содержание, формат и позицию комментария (см. «Открытые вопросы»).
2. Если согласовано:
   - открыть `backend/public/index.php`;
   - вписать комментарий в выбранную позицию;
   - проверить `php -l backend/public/index.php` (`make lint`) — синтаксис не должен сломаться;
   - `make test` — поведение не меняется, тесты остаются зелёными без правок.
3. Если в комментарии нужна ссылка на внешний документ (спека, AGENTS.md, `docs/setup/code_map.md`) — зафиксировать ссылку относительным путём от `backend/public/`.

Точный текст комментария в этом плане не приводится — он зависит от ответа заказчика.

## Тесты

- `php -l backend/public/index.php` — синтаксис остаётся валидным.
- `make test` — без изменений в ожиданиях, все существующие кейсы зелёные.
- Граничные значения для самой задачи неприменимы (комментарий не меняет поведение).
  - Если заказчик потребует, чтобы комментарий шёл **до** `<?php` / `declare(strict_types=1)` — это нужно проверить отдельно: PHPUnit/php могут не считать такой файл валидной точкой входа.

## Риски

- В `backend/public/index.php` сейчас нет ни одного комментария — введение первого комментария нужно сверить с конвенцией проекта (проверить `backend/src/**/*.php` и `tests/**`).
- Если комментарий пишется **до** `<?php`, фронт-сервер/роутер может отдать его в HTTP-ответ вместо `index.php` (для встроенного `php -S` это безопасно, для прод-настройки риск).
- Если комментарий содержит чувствительные данные (например, ссылки на внутренние хосты/секреты) — нарушает правило AGENTS.md про отсутствие реальных данных и секретов в репозитории.
- `declare(strict_types=1)` в файле уже есть — комментарий-`docblock` между `<?php` и `declare` синтаксически легален, но `declare` должен остаться самой первой исполняемой строкой.
- Эта правка **никак не относится** к задаче «LTV 62% → approve», которую риск-менеджмент ещё не одобрил — комментарий не должен её легитимизировать.

## Открытые вопросы (без заказчика не ответить)

1. **Содержание комментария.** Что именно должно быть написано? Варианты:
   - краткое описание точки входа (`AppFactory::create()->run()` собирает приложение и обслуживает HTTP);
   - ссылка на `AppFactory` / `docs/setup/code_map.md`;
   - заказчик пришлёт готовый текст следующим сообщением.
2. **ID плана.** Под каким именем сохранить файл: `plan_<ID>.md`? Какой `<ID>` использовать?
3. **Контекст.** Это отдельная мелочь или часть эпика (`MILEAGE` / продолжение обсуждения `LTV 62%` / другое)?
4. **Формат и позиция.** Однострочный `//` сразу после `<?php`, phpdoc-блок перед `declare`, или многострочный блок в конце файла?
5. **Согласование с конвенцией.** В репозитории пока нет комментариев в точке входа — подтвердить, что введение первого комментария не противоречит стилю проекта (отдельно проверить `backend/src/AppFactory.php` и соседние файлы `public/`).
6. **Связь с LTV 62%.** Если комментарий должен пояснить, почему 62% сейчас не `approve` (или наоборот — почему станет после решения риск-менеджмента) — это нужно явно подтвердить; в текущем виде правка рискует выглядеть как обход правила AGENTS.md.
