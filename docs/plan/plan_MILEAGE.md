# План MILEAGE: «пробег авто не больше 400 000 км, иначе решение review»

- ID задачи: `MILEAGE` (день 1, ДЗ.1)
- Дата плана: 2026-09-29, обновлён в тот же день после интервью Grill Me (вопросы 1–3 и 5 закрыты, п. 4 переадресован архитектору)
- Источники: `docs/setup/code_map.md` (раздел «Куда встанет правило…», scout-отчёт по пробегу приложен), `backend/config/rules.php`, `backend/src/Domain/{DecisionEngine,AssessmentService,ApplicationValidator}.php`, `backend/src/AppFactory.php`, `tests/Unit/*`, `docs/plan/README.md`, интервью Grill Me с заказчиком 2026-09-29
- Проверка после реализации: `make test`, `make lint`, ручной POST `/api/ltv` с пробегом 400 001 и с пустым/нечисловым пробегом (ожидается 422)

## Решение по дизайну (выбранный вариант)

- Правило — это правило **решения**, а не валидации, поэтому по рекомендации `code_map.md` оно встаёт в `DecisionEngine`, а не в `ApplicationValidator` и не пост-обработкой в `AssessmentService`. Альтернатива «понижать решение в `AssessmentService::assess()` после `decide()`» отклонена: решение тогда принимается в двух местах.
- Порог 400 000 не хардкодится: новый ключ `review_mileage_km` в секции `vehicle` файла `backend/config/rules.php`, рядом с существующим `max_mileage_km`. Это два разных порога: `max_mileage_km = 500 000` — валидационный предел (выше — 422), `review_mileage_km = 400 000` — порог решения (выше — review). Подтверждено заказчиком (интервью, вопрос 5).
- Семантика правила: пробег понижает `approve` до `review`; зоны `review` и `reject` по LTV правило не меняет — `reject` не смягчается. Подтверждено заказчиком (интервью, вопросы 1–2).
- Граница «не больше 400 000»: 400 000 ещё проходит без review, review начинается с 400 001 (в коде — строгое `>`). Подтверждено заказчиком (интервью, вопрос 1).
- Расширение scope по решению заказчика (интервью, вопрос 3): пустая строка и нечисловое значение поля `mileage` — ошибка валидации 422 по ключу `mileage`, а не «0 км»; числовые значения (int/float, числовые строки) приводятся к int как раньше, `0` остаётся легитимным значением. Это валидация входа, а не правило решения — противоречия с первым пунктом нет.

## 3. Тесты

Юнит-уровень `DecisionEngineTest` (провайдер: LTV, пробег, ожидаемое решение):

- LTV 28.5 + пробег 399999 → `approve`
- LTV 28.5 + пробег 400000 → `approve`
- LTV 28.5 + пробег 400001 → `review`
- LTV 72.3 (серая зона) + пробег 400001 → `review` — правило не меняет уже существующий `review`
- LTV 90.0 (зона reject) + пробег 400001 → `reject` — пробег не смягчает `reject` (подтверждено заказчиком, Вопросы п. 2)
- LTV 85.0 + пробег 400000 → `review` — существующая граница LTV не сдвинулась

Уровень сервиса `AssessmentServiceTest` (через `assess()`, фикстура LTV 50 при 450 000 из 900 000):

- пробег 399999 → `approve`, `approved_limit` = запрошенной сумме
- пробег 400000 → `approve`, `approved_limit` = запрошенной сумме
- пробег 400001 → `review`, `approved_limit` = 0 — понижение approve→review обнуляет лимит
- LTV 95 (зона reject) + пробег 450000 → `reject`, `approved_limit` = 0

Уровень валидации `ApplicationValidatorTest` (пустой/нечисловой пробег — новое поведение по решению заказчика):

- ключ `mileage` отсутствует в payload → `ValidationException`, в `errors()` есть ключ `mileage`, до расчёта решения дело не доходит
- `mileage => ''` (пустая строка) → `ValidationException` с ключом `mileage` — раньше превращалась в 0 км и проходила
- `mileage => 'abc'` (нечисловая строка) → `ValidationException` с ключом `mileage`
- `mileage => '84000'` (числовая строка) → проходит, нормализуется в 84000 — существующее приведение не ломаем

Граничные значения — отдельными строками:

- 399999 км — последний пробег до порога: решение определяется только LTV.
- 400000 км — граница «не больше 400 000»: ещё без эффекта пробега, `approve` остаётся `approve`.
- 400001 км — первый пробег за порогом: `approve` понижается до `review`.
- пустой/нечисловой пробег (нет ключа, `''`, `'abc'`) → ошибка валидации 422, решение не считается.
- 500000 км — валидационный предел `max_mileage_km` не сдвинут: 500 000 проходит валидацию (и получает `review` от нового правила при низком LTV), 500 001 — 422.

## 4. Риски

1. **Существующая проверка `max_mileage_km` (500 000, валидация).** Её не меняем и не заменяем новым порогом. Опасная рассогласованность: если `review_mileage_km` станет ≥ `max_mileage_km`, правило «пробег → review» станет мёртвым — такие заявки отсекаются валидацией раньше. Контроль: 400 000 < 500 000, в тестах есть кейс «450 000 → валидация пройдена, решение review».
2. **Ломающее изменение сигнатуры `decide()`.** После шага 3 все старые вызовы фатальны. Все места известны и включены в раздел «Файлы»: `AssessmentService.php`, `AppFactory.php`, `DecisionEngineTest.php` — других вызовов/конструкций `DecisionEngine` в коде нет (проверено scout-отчётом). Поэтому шаг 6 (правка существующего провайдера) обязателен до `make test`, иначе 6 зелёных кейсов падают с фатальной ошибкой, а не ассертом.
3. **`approved_limit` при понижении.** `review` даёт лимит 0 — это желаемое поведение, формулы лимита не трогаем (расчёт лимита по `ltv_by_age` — задача LOAN-12, отдельно).
4. **Дыра валидации пустой строки — вошла в scope по решению заказчика (интервью, вопрос 3).** `(int) ($payload['mileage'] ?? -1)` для `""` и нечисловых строк даёт 0, и заявка проходила как 0 км. Закрывается в этой задаче: проверка сырого значения до приведения (файл 2, шаг 2); контроль — тесты `''`, `'abc'`, `'84000'`. Остальные поля не трогаем: их пустая строка тоже даёт 0, но 0 отсекается их нижними границами (min год/сумма/срок), дыра только у пробега. Фронтенд не трогаем: поле `required`, из UI пустая строка не отправляется — 422 защищает прямые API-вызовы.
5. **Семантика «reject + большой пробег».** «Reject остаётся reject» — подтверждено заказчиком (интервью, вопрос 2). Если риск-менеджмент решит иначе — правка одной ветки в `DecisionEngine`, но без его решения семантику не менять (правило AGENTS.md о порогах и ожиданиях тестов).
6. **Конвенции проекта.** Порог вынесен в `rules.php` (не хардкод); существующие пороги `max_mileage_km`, `approve_max`, `review_max` и ожидания существующих тестов не меняются — новый ключ и новые кейсы только добавляются.
7. **Что НЕ входит (трогать нельзя):** фронтенд (`frontend/index.html`, `app.js`, `styles.css` — решение показывается как есть, поле «причина review» отсутствует), БД (`db/schema.sql`, `db/seed.sql` — колонка `mileage_km INT UNSIGNED` уже вмещает диапазон, сиды 20 000–296 000 км правилом не затрагиваются), `ApplicationRepository` и контроллеры, задача LOAN-12 (`ltv_by_age`), изменение `max_mileage_km`, поле `reason` в ответе API (открытый вопрос к архитектору, см. Вопросы п. 4).

## Вопросы: статус после интервью Grill Me 2026-09-29

1. Граница — **закрыта заказчиком**: 400 000 включительно — норма, review начинается с 400 001 (строгое `>`).
2. Reject по LTV + пробег > 400 000 — **закрыта заказчиком**: reject остаётся reject, смягчения нет.
3. Пустой/нечисловой пробег — **закрыта заказчиком, решение противоположно исходному предположению плана**: пустая строка и нечисловое значение → 422, вошли в scope (файл 2, шаг 2, риск 4). Отсутствие ключа `mileage` — 422, как и раньше.
4. Причина решения в ответе API (`reason`) — **открыт, переадресован архитектору**; в задачу MILEAGE не входит.
5. Порог — **закрыта заказчиком**: `review_mileage_km => 400000` отдельным ключом в `rules.php`, валидационный `max_mileage_km = 500 000` не меняется.
