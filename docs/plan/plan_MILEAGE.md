# План MILEAGE: «пробег авто не больше 400 000 км, иначе решение review»

- ID задачи: `MILEAGE` (день 1, ДЗ.1)
- Дата плана: 2026-09-29
- Источники: `docs/setup/code_map.md` (раздел «Куда встанет правило…», scout-отчёт по пробегу приложен), `backend/config/rules.php`, `backend/src/Domain/{DecisionEngine,AssessmentService,ApplicationValidator}.php`, `backend/src/AppFactory.php`, `tests/Unit/*`, `docs/plan/README.md`
- Проверка после реализации: `make test`, `make lint`, ручной POST `/api/ltv` с пробегом 400 001

## Решение по дизайну (выбранный вариант)

- Правило — это правило **решения**, а не валидации, поэтому по рекомендации `code_map.md` оно встаёт в `DecisionEngine`, а не в `ApplicationValidator` и не пост-обработкой в `AssessmentService`. Альтернатива «понижать решение в `AssessmentService::assess()` после `decide()`» отклонена: решение тогда принимается в двух местах.
- Порог 400 000 не хардкодится: новый ключ `review_mileage_km` в секции `vehicle` файла `backend/config/rules.php`, рядом с существующим `max_mileage_km`. Это два разных порога: `max_mileage_km = 500 000` — валидационный предел (выше — 422), `review_mileage_km = 400 000` — порог решения (выше — review).
- Семантика правила: пробег понижает `approve` до `review`; зоны `review` и `reject` по LTV правило не меняет — `reject` не смягчается (см. вопросы заказчику, п. 1–2).
- Граница «не больше 400 000»: 400 000 ещё проходит без review, review начинается с 400 001.

## 3. Тесты

Юнит-уровень `DecisionEngineTest` (провайдер: LTV, пробег, ожидаемое решение):

- LTV 28.5 + пробег 399999 → `approve`
- LTV 28.5 + пробег 400000 → `approve`
- LTV 28.5 + пробег 400001 → `review`
- LTV 72.3 (серая зона) + пробег 400001 → `review` — правило не меняет уже существующий `review`
- LTV 90.0 (зона reject) + пробег 400001 → `reject` — пробег не смягчает `reject` (выбранная семантика, см. Вопросы п. 2)
- LTV 85.0 + пробег 400000 → `review` — существующая граница LTV не сдвинулась

Уровень сервиса `AssessmentServiceTest` (через `assess()`, фикстура LTV 50 при 450 000 из 900 000):

- пробег 399999 → `approve`, `approved_limit` = запрошенной сумме
- пробег 400000 → `approve`, `approved_limit` = запрошенной сумме
- пробег 400001 → `review`, `approved_limit` = 0 — понижение approve→review обнуляет лимит
- LTV 95 (зона reject) + пробег 450000 → `reject`, `approved_limit` = 0

Уровень валидации `ApplicationValidatorTest` (пустой пробег, существующее поведение — фиксируем тестом):

- ключ `mileage` отсутствует в payload → `ValidationException`, в `errors()` есть ключ `mileage`, до расчёта решения дело не доходит

Граничные значения — отдельными строками:

- 399999 км — последний пробег до порога: решение определяется только LTV.
- 400000 км — граница «не больше 400 000»: ещё без эффекта пробега, `approve` остаётся `approve`.
- 400001 км — первый пробег за порогом: `approve` понижается до `review`.
- пустой пробег (нет ключа `mileage`) → ошибка валидации 422, решение не считается.
- 500000 км — валидационный предел `max_mileage_km` не сдвинут: 500 000 проходит валидацию (и получает `review` от нового правила при низком LTV), 500 001 — 422.

## 4. Риски

1. **Существующая проверка `max_mileage_km` (500 000, валидация).** Её не меняем и не заменяем новым порогом. Опасная рассогласованность: если `review_mileage_km` станет ≥ `max_mileage_km`, правило «пробег → review» станет мёртвым — такие заявки отсекаются валидацией раньше. Контроль: 400 000 < 500 000, в тестах есть кейс «450 000 → валидация пройдена, решение review».
2. **Ломающее изменение сигнатуры `decide()`.** После шага 2 все старые вызовы фатальны. Все места известны и включены в раздел «Файлы»: `AssessmentService.php`, `AppFactory.php`, `DecisionEngineTest.php` — других вызовов/конструкций `DecisionEngine` в коде нет (проверено scout-отчётом). Поэтому шаг 5 (правка существующего провайдера) обязателен до `make test`, иначе 6 зелёных кейсов падают с фатальной ошибкой, а не ассертом.
3. **`approved_limit` при понижении.** `review` даёт лимит 0 — это желаемое поведение, формулы лимита не трогаем (расчёт лимита по `ltv_by_age` — задача LOAN-12, отдельно).
4. **Дыра валидации пустой строки.** `(int) ($payload['mileage'] ?? -1)` для `""` даёт 0, и заявка проходит как 0 км; фронтенд шлёт `Number('') = 0`. Существующее поведение, в задачу не входит (см. Вопросы п. 3): тест «пустой пробег» проверяет только отсутствие ключа.
5. **Семантика «reject + большой пробег».** Выбрано «reject остаётся reject». Если риск-менеджмент решит иначе — правка одной ветки в `DecisionEngine`, но без подтверждения заказчика семантику не менять (правило AGENTS.md о порогах и ожиданиях тестов).
6. **Конвенции проекта.** Порог вынесен в `rules.php` (не хардкод); существующие пороги `max_mileage_km`, `approve_max`, `review_max` и ожидания существующих тестов не меняются — новый ключ и новые кейсы только добавляются.
7. **Что НЕ входит (трогать нельзя):** фронтенд (`frontend/index.html`, `app.js`, `styles.css` — решение показывается как есть, поле «причина review» отсутствует), БД (`db/schema.sql`, `db/seed.sql` — колонка `mileage_km INT UNSIGNED` уже вмещает диапазон, сиды 20 000–296 000 км правилом не затрагиваются), `ApplicationRepository` и контроллеры, задача LOAN-12 (`ltv_by_age`), изменение `max_mileage_km`, поле `reason` в ответе API.
