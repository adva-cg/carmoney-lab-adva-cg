# Spec MILEAGE: проверка пробега в расчёте решения по заявке

- ID задачи: `MILEAGE` (день 1, ДЗ.1)
- Дата: 2026-09-29, дополнен в тот же день по сверке с `docs/plan/plan_MILEAGE.md`
- Основан на: `docs/intent/intent_MILEAGE.md`
- Затрагиваемые границы (правки): `backend/config/rules.php`, `backend/src/Domain/ApplicationValidator.php`, `backend/src/Domain/DecisionEngine.php`, `backend/src/Domain/AssessmentService.php`, `backend/src/AppFactory.php` (передача пробега и порога в `DecisionEngine`), тесты `tests/Unit/DecisionEngineTest.php`, `tests/Unit/AssessmentServiceTest.php`, `tests/Unit/ApplicationValidatorTest.php`, документация `docs/setup/code_map.md` (после реализации). `backend/src/Http/ApplicationController.php` и `backend/src/Repository/ApplicationRepository.php` не правятся: поведение контроллера меняется транзитивно (422 по пробегу, `review` на больших пробегах), состав полей ответа не меняется. — план, раздел «Файлы», риск 7

## 1. Входит

- Новое правило решения: пробег больше 400 000 км понижает `approve` до `review` (REQ-MILEAGE-01).
- Границы правила: 400 000 включительно — норма, `review` — с 400 001 (REQ-MILEAGE-02).
- Правило не смягчает `reject` и не меняет зоны `review`/`reject` по LTV (REQ-MILEAGE-03).
- Расчёт LTV и его пороги не меняются: правило применяется к решению, а не к расчёту (REQ-MILEAGE-04).
- Порог 400 000 км хранится в `backend/config/rules.php` отдельным ключом `vehicle.review_mileage_km` (в секции `vehicle`, рядом с валидационным `max_mileage_km`), в коде не хардкодится (REQ-MILEAGE-05).
- Порог решения и валидационный предел — разные числа: `review_mileage_km` (400 000, выше — `review`) строго меньше `max_mileage_km` (500 000, выше — 422), иначе правило мёртво (REQ-MILEAGE-10).
- Понижение `approve` до `review` по пробегу обнуляет лимит: `approved_limit` = 0, как у любого не-`approve`; поля ответа не меняются (REQ-MILEAGE-09).
- Числовое `0` остаётся легитимным пробегом; числовые значения (int/float, числовые строки) приводятся к int как раньше (REQ-MILEAGE-07).
- Пустой, отсутствующий или нечисловой пробег — ошибка валидации 422, а не «0 км» (REQ-MILEAGE-06, REQ-MILEAGE-07).
- Существующий валидационный предел пробега 0–500 000 км сохраняется без изменений (REQ-MILEAGE-08).

## 2. Не входит

- Поле причины решения в ответе API (например, `reason: "high_mileage"`) — переадресовано архитектору, в задачу MILEAGE не входит. — интервью (intent, §4, §5).
- Изменение валидационного предела пробега 500 000 км и остальных существующих порогов (LTV, год, сумма, срок). — код: `backend/config/rules.php`.
- Ужесточение валидации остальных полей заявки (VIN, год, стоимость, сумма, срок) — меняется только пробег. — формулировка задачи.
- Изменения фронтенда и БД: поле пробега в форме и колонка в БД уже есть (поле в UI `required`, пустая строка из UI не отправляется; 422 по пробегу защищает прямые API-вызовы). — код: `frontend/index.html`, `db/schema.sql`; план, риск 4.
- Расчёт лимита по возрасту авто (`ltv_by_age`) — отдельная задача LOAN-12. — код: `backend/config/rules.php`.
- Изменение семантики лимита `approved_limit` (запрошенная сумма при `approve`, 0 иначе) и формул расчёта лимита. — код: `backend/src/Domain/AssessmentService.php`; план, риск 3.
- Изменение ожиданий существующих тестов: добавляются только новый ключ конфига и новые кейсы, существующие пороги и зелёные тесты не ломаются. — план, риск 6; код: `backend/config/rules.php`.

## 3. Требования и критерии приёмки

### REQ-MILEAGE-01: понижение approve до review при пробеге больше 400 000 км

Если по LTV заявка получает `approve`, но пробег больше 400 000 км, итоговое решение — `review`.

- Источник: intent §1, §3 (интервью); текущий код без учёта пробега: `backend/src/Domain/DecisionEngine.php`.

**AC-MILEAGE-01:**
- Заявка с LTV-решением `approve` и пробегом 400 001 км → решение `review`.
- Заявка с LTV-решением `approve` и пробегом 399 999 км → решение `approve`.
- Заявка с LTV-решением `approve` и пробегом 400 000 км → решение `approve`.

### REQ-MILEAGE-02: граница «не больше 400 000» включительно

400 000 км и меньше — правило не применяется, решение считается только по LTV; `review` по пробегу начинается с 400 001 км.

- Источник: intent §3, §4 (граница закрыта заказчиком в интервью).

**AC-MILEAGE-02:**
- Пробег 399 999 км: решение совпадает с решением по LTV (`approve`, `review` или `reject`).
- Пробег 400 000 км: решение совпадает с решением по LTV.
- Пробег 400 001 км: если LTV-решение `approve` — итог `review`.

### REQ-MILEAGE-03: правило не смягчает reject и не меняет зоны review/reject по LTV

Понижение до `review` действует только на `approve`. Если LTV-решение `reject`, итог остаётся `reject` при любом пробеге; если LTV-решение `review`, итог остаётся `review`.

- Источник: intent §3, §4 (закрыто заказчиком в интервью).

**AC-MILEAGE-03:**
- Заявка с LTV-решением `reject` и пробегом 400 001 км → решение `reject`.
- Заявка с LTV-решением `review` и пробегом 399 999, 400 000 или 400 001 км → решение `review`.

### REQ-MILEAGE-04: расчёт LTV и его пороги не меняются

Формула и пороги LTV (`approve_max` = 60.0, `review_max` = 85.0) не изменяются; новое правило применяется к результату решения, а не к расчёту LTV.

- Источник: intent §3 (интервью); числа: `backend/config/rules.php` (`ltv.approve_max`, `ltv.review_max`).

**AC-MILEAGE-04:**
- Значения `ltv.approve_max` и `ltv.review_max` в `backend/config/rules.php` после изменений совпадают с текущими (60.0 и 85.0).
- Для заявки с пробегом 400 000 км и меньше рассчитанный LTV и решение по LTV идентичны поведению до задачи.

### REQ-MILEAGE-05: порог 400 000 км в конфиге, не в коде

Порог 400 000 км хранится в `backend/config/rules.php` отдельным ключом `vehicle.review_mileage_km` (в секции `vehicle`, рядом с `max_mileage_km`), код читает его из конфига и не содержит бизнес-числа. Правило решения реализуется в `DecisionEngine` (это правило решения, а не валидация в `ApplicationValidator` и не пост-обработка в `AssessmentService`).

- Источник: intent §3 (порог — интервью); имя ключа — интервью, вопрос 5 (план, «Решение по дизайну»); место правила — рекомендация `docs/setup/code_map.md`; конвенция «бизнес-числа не хардкодим» — `AGENTS.md`, `backend/config/rules.php`.

**AC-MILEAGE-05:**
- В `backend/config/rules.php` в секции `vehicle` присутствует ключ `review_mileage_km` со значением `400000`.
- В `backend/src/Domain/DecisionEngine.php` и других классах `backend/src/` нет литерала `400000`/`400 000`.

### REQ-MILEAGE-06: пустой или отсутствующий пробег — ошибка валидации

Если поле `mileage` отсутствует в payload или является пустой строкой, заявка не проходит валидацию (422), решение не считается. Пустая строка не приводится к 0 км. Ошибка выдаётся по ключу `mileage` с существующим текстом диапазона («Пробег от 0 до N км»), новых текстов ошибок не вводится.

- Источник: intent §3 (интервью + код); текущее поведение: `backend/src/Domain/ApplicationValidator.php:43-46` — отсутствие ключа уже сейчас даёт -1 → 422 (`?? -1`, существующее поведение сохраняется), дыра только у пустой строки: `(int) ''` = 0 проходит; `backend/src/Http/ApplicationController.php`. Текст ошибки — план, раздел «Файлы», п. 2.

**AC-MILEAGE-06:**
- Заявка без поля `mileage` → HTTP 422 с ошибкой по полю `mileage`, решение не вычисляется (существующее поведение сохраняется).
- Заявка с `mileage: ""` → HTTP 422 с ошибкой по полю `mileage`, решение не вычисляется (новое поведение: раньше пустая строка трактовалась как 0 км и проходила валидацию).

### REQ-MILEAGE-07: нечисловой пробег — ошибка валидации

Если поле `mileage` содержит нечисловое значение (например, строку `"abc"`), заявка не проходит валидацию (422), значение не приводится к 0. Числовые значения (int/float) и числовые строки приводятся к int как раньше; `0` остаётся легитимным значением пробега, а не «пустым».

- Источник: intent §3 (интервью); текущий код приведения: `backend/src/Domain/ApplicationValidator.php:43`.

**AC-MILEAGE-07:**
- Заявка с `mileage: "abc"` → HTTP 422 с ошибкой по полю `mileage`.
- Заявка с `mileage: "400000"` (числовая строка) → валидация проходит, значение трактуется как 400 000 км — поведение согласуется с существующей обработкой числовых строк.
- Заявка с `mileage: 0` → валидация проходит, трактуется как 0 км — легитимное значение; приведение int/float/числовых строк к int не меняется.

### REQ-MILEAGE-08: валидационный предел 0–500 000 км сохраняется

Диапазон валидации пробега 0–500 000 км остаётся: пробег меньше 0 или больше 500 000 — ошибка валидации (422), до расчёта решения заявка не доходит. Новое правило (400 000) этот предел не заменяет и не изменяет.

- Источник: intent §3 (код); число 500 000: `backend/config/rules.php` (`vehicle.max_mileage_km`), `backend/src/Domain/ApplicationValidator.php:44-45`.

**AC-MILEAGE-08:**
- Заявка с пробегом 500 000 км → валидация проходит; если LTV-решение `approve` — итог `review` (правило REQ-MILEAGE-01).
- Заявка с пробегом 500 001 км → HTTP 422, решение не вычисляется.
- Заявка с пробегом -1 → HTTP 422, решение не вычисляется.

### REQ-MILEAGE-09: понижение до review обнуляет approved_limit, поля ответа не меняются

`approved_limit` выдаётся только при `approve`: заявка, пониженная до `review` по пробегу, получает `approved_limit` = 0, как и любой другой не-`approve` ответ. Существующая семантика лимита (запрошенная сумма при `approve`, 0 иначе) и формулы лимита не меняются; расчёт лимита по возрасту (`ltv_by_age`) — задача LOAN-12. Состав полей ответа не меняется: `vehicle_age`, `ltv`, `decision`, `approved_limit`, `input`.

- Источник: существующий код `backend/src/Domain/AssessmentService.php:39`; план, раздел «Тесты» (уровень сервиса). Производное требование от REQ-MILEAGE-01/REQ-MILEAGE-03: фиксирует неизменность существующей семантики лимита, новых бизнес-решений не вводит.

**AC-MILEAGE-09:**
- Заявка с LTV-решением `approve` и пробегом 400 001 км → `decision: review`, `approved_limit: 0`.
- Заявка с LTV-решением `approve` и пробегом 400 000 км → `decision: approve`, `approved_limit` равен запрошенной сумме.
- Заявка с LTV-решением `reject` и пробегом 450 000 км → `decision: reject`, `approved_limit: 0`.
- Состав полей ответа API после изменений совпадает с текущим (новых полей, включая `reason`, нет).

### REQ-MILEAGE-10: инвариант конфига — порог решения ниже валидационного предела

`vehicle.review_mileage_km` (порог решения) должен быть строго меньше `vehicle.max_mileage_km` (валидационный предел). Это два разных порога: если порог решения станет ≥ валидационного предела, правило «пробег → review» станет мёртвым — заявки с таким пробегом отсекаются валидацией (422) раньше, чем дойдут до расчёта решения.

- Источник: производный инвариант от REQ-MILEAGE-05 и REQ-MILEAGE-08; план, риск 1; значения (400 000 < 500 000) подтверждены заказчиком (интервью, вопрос 5).

**AC-MILEAGE-10:**
- После изменений в `backend/config/rules.php`: `vehicle.review_mileage_km` = 400000 и меньше `vehicle.max_mileage_km` = 500000.
- Заявка с пробегом 450 000 км (между порогами) → валидация проходит; при LTV-решении `approve` итог `review` — правило достижимо при текущих значениях конфига.

## 4. Open questions из intent — статус

- Граница «не больше 400 000» — закрыт заказчиком (интервью), учтено в REQ-MILEAGE-02. Дополнительных вопросов нет.
- Перекрывает ли правило `reject` — закрыт заказчиком (интервью), учтено в REQ-MILEAGE-03.
- Пустой/нечисловой пробег — закрыт заказчиком (интервью), учтено в REQ-MILEAGE-06, REQ-MILEAGE-07.
- Поле причины решения в ответе API (`reason: "high_mileage"`) — **остаётся открытым**: заказчик переадресовал архитектору; в MILEAGE не входит, зафиксировано в разделе «Не входит». В спеку новых требований по нему не добавлено.
- Ключ конфига для порога решения — закрыт заказчиком (интервью, вопрос 5): `vehicle.review_mileage_km => 400000` отдельным ключом в `rules.php`, валидационный `max_mileage_km = 500000` не меняется. Учтено в REQ-MILEAGE-05 и REQ-MILEAGE-10.
